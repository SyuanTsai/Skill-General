# Optional Git ref storage adapter

Load `../scripts/GitRefHandoffAdapter.psm1` only after the adopting user has selected a Git remote for Task Handoff storage, configured an isolated local Git object store with that remote, chosen an opaque Authority Scope, and supplied trusted principal resolution plus an authorization policy. Git is one optional storage choice. Each task's formal authority and mutable Source still come from the adopter's configured task-type rules and must be revalidated before integration; the Git ref SHA is only the storage revision.

The remote must support writes to a dedicated `refs/heads/handoff-v1` namespace and the explicit expected SHA form of `--force-with-lease`. Limit writers to that namespace if the host supports it. Do not point the module at a general application source repository unless the adopter has explicitly designated its dedicated Handoff refs for storage. Configure authentication through the host's normal private credential mechanism; this module neither obtains nor stores credentials, and a protected or unavailable ref stops the Handoff mutation. No operation writes a regular source branch, Notion page, Jira issue, or another selected authority.

## Capability status

- Supported: when selected and configured, the existing `GitRefHandoffAdapter.psm1` is an implemented opt-in Git adapter. It is not a global default and is not the task's formal authority.
- Selected Git is unavailable when the required remote, policy, CAS/expected-lease behavior, or readback is missing or unavailable; state that durable Git saving did not complete and do not fall back.
- A missing or unavailable connector that was not selected must not block the Git adapter and must not be probed or required as a fallback.

On Windows, full SHA-256 record refs under a deeply nested **local bare remote** can exceed Git's default path capacity. A controlled local test showed that `core.longpaths=true` on the isolated bare remote allowed that exact ref to be written and read back; an adopting user must verify the selected host's behavior and may instead use a shorter isolated Git store path. Exact reads disable the configured fetch refmap, so opaque Handoff refs enter object storage and `FETCH_HEAD` without being mirrored under a writer clone's longer `refs/remotes/origin/...` path. The module never changes Git configuration. A ref that remains absent after a rejected create-only push is an unverified storage write, not evidence of a competing revision. Only a different observed remote SHA is a conditional revision conflict. Preserve the Operation ID and inspect the selected remote's ref path, permissions, and long-ref support before retrying.

## Mapping

- `New-GitHandoffAdapter` takes `RepositoryRoot`, `AuthorityScope`, `GetVerifiedPrincipal`, `Authorize`, `RemoteName`, and a safe `RefPrefix`. The principal resolver must obtain identity from trusted host context; the policy receives that principal plus Authority Scope, Task Key, optional Branch or Fork ID, and action. It must return exactly Boolean true. Missing, failed, or denied evaluation stops before record content is read or written. The adopter must opt in and separately establish remote permission; creation does not create the remote or Handoff data.
- A common scoped Task Key and each exact peer Branch ID map to separate ref names containing full SHA-256 identities. The record and recovery namespaces hash Authority Scope and Task Key independently, concatenate those two fixed-width digests, and hash that fixed-width value again; branch and Fork IDs use separate full digests. A delimiter, including NUL, inside a legal component therefore cannot alias another tuple. Record IDs independently bind the Authority Scope and logical identifiers. A per-field event applies the same fixed-width component-hash construction to Operation ID, scoped Record ID, and Field identity. Stored JSON retains Authority Scope and original identifiers; readback rejects a ref with a different scope or identity.
- `New-GitHandoffCommon` and `New-GitHandoffBranch` require a nonempty caller-supplied display `Actor` label and use create-only empty expected leases. The label is descriptive provenance and is never trusted for authorization; every write separately resolves and stores the verified principal from trusted host context. The adapter owns Authority Scope and initializes each branch Continuation Generation to `0`; callers cannot supply either system field. Creation also rejects an `Active Branches` or `Last Activity At` field because only canonical reconciliation and material writes may manage them. Every recognized contract field must use its exact canonical spelling and case, so a differently cased key cannot bypass Lifecycle, Work State, Branch Outcome, identity, generation, or structural-index checks. A new branch requires one exact Pending fork recovery, a target-to-operation binding, an attested Fork Point and creation fields digest, and an Active common record. The branch ref and a no-op common fence revision are pushed atomically with exact leases; a common revision race leaves no branch record. Restore an Archived common through explicit continuation before branch creation. `Set-GitHandoffFields` requires the exact revision returned by `Get-GitHandoffCommon` or `Get-GitHandoffBranch`, plus one stable Operation ID, and validates the complete resulting record so an update cannot clear a required field. Branch Lifecycle changes must use `Set-GitHandoffBranchLifecycle`; direct field mutation is rejected so the common Active index cannot be skipped. Before recording a confirmed common branch decision, call `Get-GitHandoffBranchReviewBinding` for every affected branch and store the returned exact branch revision, reviewed-content SHA-256, Continuation Generation, and intended outcome in `Decision Branch Bindings`. A usable decision revision must itself originate exactly one newly committed, decision-confirmed binding change; a later ordinary revision cannot inherit those bindings as fresh authority. The adapter rejects malformed, duplicate, stale, generation-mismatched, or content-mismatched bindings before the common write. Re-read both the remote ref and the record after writing; a peer revision conflict is a stop and formal Source revalidation, never a blind replay.
- A committed record atomically keeps Authority Scope, the operation digest, every changed field, and one complete durable event intent per field. The operation and each intent bind the immutable `VerifiedPrincipal` resolved from trusted host context, alongside the caller's display Actor, Authority Scope, Operation ID, Record ID, previous/new state, time, reason, Source, and integration status before the record ref becomes visible. Each final event uses its own immutable create-only ref and adds the verified record revision/readback result; if an event push fails, a replacement writer retries the **same** operation ID and reconstructs the event only from the committed intent, preserving the original principal even when a different authorized principal performs reconciliation. The adapter finds the operation's original first-parent commit and verifies its Authority Scope and principal evidence, so a later peer edit of the same field cannot rewrite or erase the earlier event. A branch created without a successfully updated common Active index remains recoverable by its exact authorized Branch ID; repeat its original operation to finish the index.
- For a Work State or Branch Outcome transition, supply a concrete `Reason` and a traceable `Actor` when calling `Set-GitHandoffFields`; use `Set-GitHandoffBranchLifecycle` for branch Lifecycle. The adapter rejects a transition without a reason. A decision-bound Branch Outcome operation may change only Branch Outcome, and decision-driven archival requires the matching outcome to be durable first. The event retains previous and new state, original operation time, Reason, Actor, the complete scalar or structured Source value from its record commit, structural or branch integration status, and verified readback. Retrying a committed operation finishes its pending events before evaluating current decision, content, or continuation-generation fences, so stale state cannot strand immutable evidence.
- Adapter-owned index and common-restore mutations use the reserved `__handoff_internal_v1__:` Operation ID namespace. The ID binds its purpose, parent public operation, exact task/branch identity, and observed revision state. Public create and update calls reject adopter-supplied IDs in that namespace, while older public text such as `${OperationId}:index` remains available to a legitimate unrelated operation and cannot collide with the adapter's structural mutation.
- Call `Start-GitHandoffBranchContinuation` before resumed work or forking from an existing branch. It routes through `Set-GitHandoffBranchLifecycle` with explicit continuation, increments Continuation Generation even when the branch is already Active, and restores only that branch plus its common index when Archived. One stable continuation Operation ID owns one increment; retries must retain the same operation, actor, reason, and generation transition. `Set-GitHandoffBranchLifecycle` also archives one exact branch and conditionally removes its common index entry. For an archive driven by a user decision, pass the same `DecisionCommonRevision` used for its Branch Outcome. The adapter derives the branch binding from that immutable common decision and verifies the common identity, reviewed branch content, and unchanged Continuation Generation immediately before and after the branch mutation and again after index reconciliation. Later common revisions are accepted only when they descend from the bound revision and preserve every common decision field, so other branches may change only the structural Active index. A branch revision may advance through outcome and archive finalization because Lifecycle and Branch Outcome are excluded from reviewed-content identity; Continuation Generation remains included, so any explicit continuation or user-reviewable content change requires renewed user confirmation and a new binding. The operation and event retain `DecisionCommonRevision`, `DecisionBranchRevision`, `DecisionBranchContentSha256`, and `DecisionBranchContinuationGeneration`. A retry must retain the same operation ID, all decision bindings, actor, and reason; an already Archived branch without that matching operation cannot synthesize a decision-bound archive event. It forwards the supplied Actor to both the branch and structural-index events. Before and after each common index mutation it re-reads the exact branch revision, lifecycle, and generation; if a concurrent archive or continuation supersedes the caller's state, reconciliation follows the latest durable branch revision with a stable revision-bound internal operation ID until branch and index agree. Every committed internal index operation associated with the public lifecycle operation is discovered from the common record and has its event completed, including an older operation whose event failed before a newer reconciliation began. Before an Active branch is added to the index, the exact common Lifecycle is re-read and an Archived common is conditionally restored with a revision-bound internal operation; a concurrent re-archive causes another read/restore cycle rather than an Archived common with an Active branch. A failed index write is a reported durable branch with a pending common step. Do not archive common while its Active index still contains any branch; archive changes Lifecycle alone and does not reset last material activity. The daily enumerator and inactivity scheduler remain separate SYP-217 work.

`Branch Outcome` is permitted only for branch records with an allowed value, an explicit `DecisionConfirmed` call, and the exact `DecisionCommonRevision` after the Skill has verified the user's decision and common readback. These arguments express an already-established Gate; they are not authorization or independent proof. The trusted adapter policy authorizes the operation separately, and the adapter then looks up that common revision's `Decision Branch Bindings`; callers cannot substitute a different reviewed branch revision, content identity, or Continuation Generation during finalization. Preserve the common and branch decision revisions, reviewed-content SHA-256, reviewed generation, Source, and concrete Reason in the operation and event. A semantic common-field change, reviewed branch content change, or any explicit continuation rejects the stale branch write even when the branch remains Active and its other content has not changed. Configure the Git author identity in the isolated object store separately. An event Actor is an adopter-supplied display label and can never establish who was authenticated; use the immutable Verified Principal for security attribution and access-control evidence. If policy evaluation, Git ref force-with-lease semantics, exact lookup, remote permission, or a signed release Gate is unavailable, report durable v1 saving as incomplete; do not fall back to last-write-wins Notion page writes.

## Isolated first-fork recovery

Fix the pre-fork common revision, original A host identity and distinct A/B Branch IDs. Before creating branches, authorize the exact fork action and call `New-GitHandoffForkRecovery` with an exact Fork ID and a payload containing Fork Point, Source Branch ID, Intended Branch IDs, the exact Source Snapshot, independently verified Shared Baseline, Verified Active Branches, an exact `Branch Creation Operations` map, and stable Step Operation IDs. The map has exactly one distinct stable creation Operation ID for each absent target and no extra target. The module verifies that Verified Active Branches equal the exact scoped common index and that every Fork Point equals the verified common revision. When Source Branch ID resolves to an existing indexed branch, it authorizes and reads that live branch before admission, requires Active Lifecycle plus exact Current/Source, and persists its Branch ID, revision, Fork Point, and Continuation Generation in the protected control; a common-only fork must not silently reuse an existing source branch. It creates the payload-free Pending envelope, separately protected control record, minimal Pending index, and a payload-free no-op common revision fence in one atomic four-ref push with absent-value leases plus the exact expected common lease, then reads back all four before writing the isolated snapshot payload. The common fence advances only the common storage cursor from the verified revision and preserves the common document; a stale common writer therefore fails its lease. Rejecting any member leaves all four refs at their prior state. The control retains the raw source locator, source ACL locator and live binding, raw target-to-operation map, expected branch creation digests, payload locator/digest, verified common revision, and a digest of common semantic state. The listable envelope and index expose only hashes and status. A retry with the complete initial set but no payload revalidates the control and common semantic fence before writing the payload; payload creation atomically writes the isolated payload and the envelope's `Payload Revision` under the envelope lease. An incomplete initial set fails closed and is never repaired piecemeal.

`Get-GitHandoffPendingForkRecoveries` enumerates only the minimal recovery-index namespace. It validates and authorizes each exact Fork ID before returning the item and never loads an envelope, control record, or payload. The common-archival safety check reads every protected index entry without applying list-item filtering and returns only a blocker, so an unseen Pending recovery cannot be mistaken for an empty set. Only an authorized `Get-GitHandoffForkRecovery` for the exact Fork ID loads and cross-validates all three protected objects; it reads the payload-free control and authorizes its bound source branch before fetching `recovery.json`. Before `New-GitHandoffBranch` writes a matching target, it requires that full validation, verifies the raw target-to-operation binding and common semantic digest, then conditionally records a claim binding the common, payload, control, and expected branch-payload revisions/digests. The proposed Fork Point, Current, Source, Lifecycle, and Work State must reproduce the attested digest exactly. The branch persists those recovery bindings, and its create-only ref is pushed atomically with the claimed common revision fence. If any protected object is missing, stale, unauthorized, or mismatched, branch creation stops.

If the payload write fails, the minimal index remains Pending and blocks unsafe auto-resume and common archival. An authorized `Abandon-GitHandoffForkRecovery` reads the protected control only after exact authorization, uses its raw target identities for per-branch authorization and absence proof, and can release the block only when the payload ref and envelope `Payload Revision` are both absent, target records and claims are absent. It creates the Abandoned envelope and matching terminal index commits locally, then pushes both refs atomically under their exact leases and reads both back. Rejecting either ref leaves both Pending. Payload creation atomically advances the envelope's `Payload Revision`, and its compare-and-swap competes with branch claims and abandonment on the same envelope revision, so a payload/target write and Abandoned transition cannot both start successfully.

A restarted writer reads that exact recovery record and A/B refs, validates the identities, and resumes only missing steps with the same operation IDs; it must not recover A from process memory or a common event. Incomplete or unverifiable payload remains Pending and stops branch creation. B starts from the confirmed shared baseline with its own Current/Source and a traceable fork reference. If authority cannot distinguish a fact from an A-only candidate, leave it in A and keep recovery Pending.

Call `New-GitHandoffBranch` for the original A identity first, using the persisted A snapshot exactly, then for B using the persisted verified shared baseline exactly, with the same attested Fork Point, separate stable operation IDs, and each display Actor label plus trusted Verified Principal evidence. The module verifies each branch record/event and conditionally indexes that exact Branch ID. Read back A and B, their recovery bindings, Task Key/Fork Point/Current/Source, and both common Active index entries. Only then use one conditional `Set-GitHandoffFields` operation to write both common Current and Source as confirmed shared state with A/B provenance and read back both fields/events. The original A-only Source remains in A and the isolated recovery record, never common. Finally call `Complete-GitHandoffForkRecovery` with the exact Pending payload revision and a stable completion Operation ID. Completion first verifies every target's bound operation, persisted recovery metadata, creation-payload digest, and Active index entry, then commits and reads back the payload as Completed. The initial common fence is a durable common-ref storage cursor advanced by a payload-free no-op commit; it is not a separate lock ref, and later bound branch/index or terminal common reconciliation advances the same common cursor. Completion next atomically pushes the Completed envelope, preserving its `Payload Revision`, and matching terminal index under both exact leases and reads back the full terminal set. Rejecting either terminal ref leaves both Pending for the same operation to retry. After completion, A and B may independently advance their own branches. If A already has a branch, call `Start-GitHandoffBranchContinuation` and read back its incremented generation before taking the exact snapshot; persist that post-fence revision/generation and stable continuation Operation ID in the smaller recovery payload, then create only B. If A advances after recovery is durable, preserve its newer state and create B from the persisted shared baseline; do not copy A's post-fork work into B.

If a second branch or index write is uncertain, retain the original IDs and Pending recovery record. A branch may exist by exact Branch ID while absent from common Active index; retry `New-GitHandoffBranch` with the **same** operation ID and fields to reconcile only its missing event/index step. A Task Key-only singleton lookup cannot treat a Pending recovery envelope as finished. Do not copy an unselected A candidate to B, promote it to common, write branch-only progress to common, expose the recovery payload through envelope listing, or complete recovery before both branch/index/common readbacks.

## Controlled test boundary

`tests/GitRefHandoffAdapter.Tests.ps1` uses an isolated local bare Git remote and separate writer clones. It covers required trusted-principal authorization, per-item denied recovery listing, cross-scope isolation, strict Unicode hashing, duplicate common create, display Actor plus immutable Verified Principal evidence, atomic envelope/control/index bootstrap rollback, atomic Completed and Abandoned envelope/index rollback plus retry, minimal-index recovery listing after payload failure, protected control validation, authorized abandonment, non-reusable Abandoned Fork IDs, payload and branch-claim abandonment blocks, Pending common protection, attested and atomically fenced branch creation, delimiter-safe record identity, stale common CAS, two peer branches, reviewed branch revision/content/generation binding, decision-origin and outcome-before-archive enforcement, renewed confirmation after content or generation changes, finalization and continuation event recovery before stale checks, record/event and branch/index partial failure, reserved internal identities, every committed lifecycle-index event after concurrent reconciliation, scalar and structured Source provenance, canonical field casing, required-field preservation, exact archival/restore, common revalidation before restore indexing, lifecycle Actor propagation, deterministic concurrent races, Windows long-ref behavior, and common protection. This is an implementation test, not an adopter's actual remote, cross-environment installation, or a trusted signed release receipt. For a live E2E, choose the storage remote and policy, test two actual writer environments and denied callers, record ref SHA and readbacks, and document rollback and permissions separately.
