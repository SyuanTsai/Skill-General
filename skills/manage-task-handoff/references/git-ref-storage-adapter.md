# Optional Git ref storage adapter

Load `../scripts/GitRefHandoffAdapter.psm1` only after the adopting user has selected a Git remote for Task Handoff storage, configured an isolated local Git object store with that remote, chosen an opaque Authority Scope, and supplied trusted principal resolution plus an authorization policy. Git is one optional storage choice. Each task's formal authority and mutable Source still come from the adopter's configured task-type rules and must be revalidated before integration; the Git ref SHA is only the storage revision.

The remote must support writes to a dedicated `refs/heads/handoff-v1` namespace and the explicit expected SHA form of `--force-with-lease`. Limit writers to that namespace if the host supports it. Do not point the module at a general application source repository unless the adopter has explicitly designated its dedicated Handoff refs for storage. Configure authentication through the host's normal private credential mechanism; this module neither obtains nor stores credentials, and a protected or unavailable ref stops the Handoff mutation. No operation writes a regular source branch, Notion page, Jira issue, or another selected authority.

On Windows, full SHA-256 record refs under a deeply nested **local bare remote or writer clone** can exceed Git's default path capacity. A controlled local test showed that `core.longpaths=true` on both the isolated bare remote and each writer clone allowed that exact ref to be written and read back; an adopting user must verify the selected host's behavior and may instead use a shorter isolated Git store path. The module never changes Git configuration. A ref that remains absent after a rejected create-only push is an unverified storage write, not evidence of a competing revision. Only a different observed remote SHA is a conditional revision conflict. Preserve the Operation ID and inspect the selected remote's ref path, permissions, and long-ref support before retrying.

## Mapping

- `New-GitHandoffAdapter` takes `RepositoryRoot`, `AuthorityScope`, `GetVerifiedPrincipal`, `Authorize`, `RemoteName`, and a safe `RefPrefix`. The principal resolver must obtain identity from trusted host context; the policy receives that principal plus Authority Scope, Task Key, optional Branch or Fork ID, and action. It must return exactly Boolean true. Missing, failed, or denied evaluation stops before record content is read or written. The adopter must opt in and separately establish remote permission; creation does not create the remote or Handoff data.
- A common scoped Task Key and each exact peer Branch ID map to separate ref names containing full SHA-256 identities. The record and recovery namespaces use one full digest over Authority Scope, a zero delimiter, and Task Key, preserving scoped isolation without adding Windows ref depth; branch and Fork IDs use separate full digests. Record IDs independently bind the Authority Scope and logical identifiers, so legal values containing delimiters cannot alias another tuple. A per-field event maps to a full SHA-256 of the composite Operation ID, scoped Record ID, and Field identity. Stored JSON retains Authority Scope and original identifiers; readback rejects a ref with a different scope or identity.
- `New-GitHandoffCommon` and `New-GitHandoffBranch` require the adopter's nonempty actual writer `Actor` and use create-only empty expected leases. The adapter owns Authority Scope and initializes each branch Continuation Generation to `0`; callers cannot supply either system field. Creation also rejects an `Active Branches` or `Last Activity At` field because only canonical reconciliation and material writes may manage them. Every recognized contract field must use its exact canonical spelling and case, so a differently cased key cannot bypass Lifecycle, Work State, Branch Outcome, identity, generation, or structural-index checks. A new branch requires the exact common record to be Active; restore an Archived common through explicit continuation before branch creation. `Set-GitHandoffFields` requires the exact revision returned by `Get-GitHandoffCommon` or `Get-GitHandoffBranch`, plus one stable Operation ID, and validates the complete resulting record so an update cannot clear a required field. Before recording a confirmed common branch decision, call `Get-GitHandoffBranchReviewBinding` for every affected branch and store the returned exact branch revision, reviewed-content SHA-256, Continuation Generation, and intended outcome in `Decision Branch Bindings`. The adapter rejects malformed, duplicate, stale, generation-mismatched, or content-mismatched bindings before the common write. One refspec per push implements a single-record conditional mutation. Re-read both the remote ref and the record after writing; a peer revision conflict is a stop and formal Source revalidation, never a blind replay.
- A committed record atomically keeps Authority Scope, the operation digest, every changed field, and one complete durable event intent per field. Each intent binds Authority Scope, Operation ID, Record ID, previous/new state, actor/time, reason, Source, and integration status before the record ref becomes visible. Each final event uses its own immutable create-only ref and adds the verified record revision/readback result; if an event push fails, a replacement writer retries the **same** operation ID and reconstructs the event only from the committed intent. The adapter finds the operation's original first-parent commit and verifies its Authority Scope, so a later peer edit of the same field cannot rewrite or erase the earlier event. A branch created without a successfully updated common Active index remains recoverable by its exact authorized Branch ID; repeat its original operation to finish the index.
- For a Lifecycle, Work State, or Branch Outcome transition, supply a concrete `Reason` and a traceable `Actor` when calling `Set-GitHandoffFields`; the adapter rejects a transition without a reason. The event retains previous and new state, original operation time, Reason, Actor, the complete scalar or structured Source value from its record commit, structural or branch integration status, and verified readback. Retrying an already committed common index must also finish every pending per-field event for that parent operation before reporting the index complete.
- Adapter-owned index and common-restore mutations use the reserved `__handoff_internal_v1__:` Operation ID namespace. The ID binds its purpose, parent public operation, exact task/branch identity, and observed revision state. Public create and update calls reject adopter-supplied IDs in that namespace, while older public text such as `${OperationId}:index` remains available to a legitimate unrelated operation and cannot collide with the adapter's structural mutation.
- `Set-GitHandoffBranchLifecycle` archives one exact branch and conditionally removes its common index entry, or restores only that branch on explicit continuation and conditionally adds the index entry. An Archived-to-Active restore atomically changes Lifecycle and increments Continuation Generation once; retries must retain the same operation, actor, reason, and generation transition. For an archive driven by a user decision, pass the same `DecisionCommonRevision` used for its Branch Outcome. The adapter derives the branch binding from that immutable common decision and verifies the common identity, reviewed branch content, and unchanged Continuation Generation immediately before and after the branch mutation and again after index reconciliation. Later common revisions are accepted only when they descend from the bound revision and preserve every common decision field, so other branches may change only the structural Active index. A branch revision may advance through outcome and archive finalization because Lifecycle and Branch Outcome are excluded from reviewed-content identity; Continuation Generation remains included, so any explicit restore or user-reviewable content change requires renewed user confirmation and a new binding. The operation and event retain `DecisionCommonRevision`, `DecisionBranchRevision`, `DecisionBranchContentSha256`, and `DecisionBranchContinuationGeneration`. A retry must retain the same operation ID, all decision bindings, actor, and reason; an already Archived branch without that matching operation cannot synthesize a decision-bound archive event. It forwards the supplied Actor to both the branch and structural-index events. Before and after each common index mutation it re-reads the exact branch revision, lifecycle, and generation; if a concurrent archive or restore supersedes the caller's state, reconciliation follows the latest durable branch revision with a stable revision-bound internal operation ID until branch and index agree. Every committed internal index operation associated with the public lifecycle operation is discovered from the common record and has its event completed, including an older operation whose event failed before a newer reconciliation began. Before an Active branch is added to the index, the exact common Lifecycle is re-read and an Archived common is conditionally restored with a revision-bound internal operation; a concurrent re-archive causes another read/restore cycle rather than an Archived common with an Active branch. A failed index write is a reported durable branch with a pending common step. Do not archive common while its Active index still contains any branch; archive changes Lifecycle alone and does not reset last material activity. The daily enumerator and inactivity scheduler remain separate SYP-217 work.

`Branch Outcome` is permitted only for branch records with an allowed value, an explicit `DecisionConfirmed` call, and the exact `DecisionCommonRevision` after the Skill has verified the user's decision and common readback. These arguments express an already-established Gate; they are not authorization or independent proof. The trusted adapter policy authorizes the operation separately, and the adapter then looks up that common revision's `Decision Branch Bindings`; callers cannot substitute a different reviewed branch revision, content identity, or Continuation Generation during finalization. Preserve the common and branch decision revisions, reviewed-content SHA-256, reviewed generation, Source, and concrete Reason in the operation and event. A semantic common-field change, reviewed branch content change, or explicit restore rejects the stale branch write even when the branch's own expected revision still matches. Configure the Git author identity in the isolated object store separately; an event Actor is supplied by the adopter's actual writer and must not be inferred from an unverified Git identity or treated as the access-control principal. If policy evaluation, Git ref force-with-lease semantics, exact lookup, remote permission, or a signed release Gate is unavailable, report durable v1 saving as incomplete; do not fall back to last-write-wins Notion page writes.

## Isolated first-fork recovery

Fix the pre-fork common revision, original A host identity and distinct A/B Branch IDs. Before creating branches, authorize the exact fork action and call `New-GitHandoffForkRecovery` with an exact Fork ID and a payload containing Fork Point, Source Branch ID, Intended Branch IDs, the exact Source Snapshot, independently verified Shared Baseline, Verified Active Branches, and stable Step Operation IDs. The module binds Authority Scope into its identity, writes the document to a dedicated create-only recovery ref, and reads it back; it never writes the snapshot into common or branch fields or their field-event refs. `Get-GitHandoffPendingForkRecoveries` returns only authorized scoped Task Key, Fork ID, status, and revision envelopes so normal recall can block unsafe singleton auto-resume without exposing branch snapshots. Only an authorized `Get-GitHandoffForkRecovery` for the exact Fork ID returns the payload to reconciliation, with policy at least as strict as its source branch.

A restarted writer reads that exact recovery record and A/B refs, validates the identities, and resumes only missing steps with the same operation IDs; it must not recover A from process memory or a common event. Incomplete or unverifiable payload remains Pending and stops branch creation. B starts from the confirmed shared baseline with its own Current/Source and a traceable fork reference. If authority cannot distinguish a fact from an A-only candidate, leave it in A and keep recovery Pending.

Call `New-GitHandoffBranch` for the original A identity first, using the persisted A snapshot, then for B using the persisted verified shared baseline, with the **same** pre-fork revision as Fork Point, separate stable operation IDs, and each actual writer Actor. The module creates each branch ref with an empty expected lease, verifies its record/events, and conditionally indexes that exact Branch ID. Read back A and B, their Task Key/Fork Point/Current/Source, and both common Active index entries. Only then use one conditional `Set-GitHandoffFields` operation to write **both** common Current and Source as confirmed shared state with A/B provenance and read back both fields/events. The original A-only Source remains in A and the isolated recovery record, never common. Finally call `Complete-GitHandoffForkRecovery` with the exact Pending revision and a stable completion Operation ID. After that verified conversion, A and B may independently advance their own branches. If A already has a branch, revalidate it, persist the smaller exact recovery payload, and create only B. If A advances after recovery is durable, preserve its newer state and create B from the persisted shared baseline; do not require undeclared historical-revision lookup or copy A's post-fork work.

If a second branch or index write is uncertain, retain the original IDs and Pending recovery record. A branch may exist by exact Branch ID while absent from common Active index; retry `New-GitHandoffBranch` with the **same** operation ID and fields to reconcile only its missing event/index step. A Task Key-only singleton lookup cannot treat a Pending recovery envelope as finished. Do not copy an unselected A candidate to B, promote it to common, write branch-only progress to common, expose the recovery payload through envelope listing, or complete recovery before both branch/index/common readbacks.

## Controlled test boundary

`tests/GitRefHandoffAdapter.Tests.ps1` uses an isolated local bare Git remote and separate writer clones. It covers required trusted-principal authorization, denied and unavailable policy, cross-scope isolation for the same Task Key, duplicate common create, required creation actor, pre-write structural-index rejection, delimiter-safe record identity, stale common CAS, two peer branches, reviewed branch revision/content/generation binding, malformed and duplicate binding rejection, renewed confirmation after reviewed content changes or explicit restore, per-field event retry, record/event and branch/index partial failure, reserved internal identities, an already committed index with a pending event, every committed lifecycle-index event after concurrent reconciliation, later same-field edits, scalar and structured Source provenance, canonical field casing, invalid states, required-field preservation, Archived-common branch rejection, exact archival/restore, common revalidation before restore indexing, lifecycle Actor propagation, deterministic concurrent archive/restore races, and common protection. This is an implementation test, not an adopter's actual remote, cross-environment installation, or a trusted signed release receipt. For a live E2E, choose the storage remote and policy, test two actual writer environments and denied callers, record ref SHA and readbacks, and document rollback and permissions separately.
