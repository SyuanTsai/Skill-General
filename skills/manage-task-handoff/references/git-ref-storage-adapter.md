# Optional Git ref storage adapter

Load `../scripts/GitRefHandoffAdapter.psm1` only after the adopting user has selected a Git remote for Task Handoff storage and configured an isolated local Git object store with that remote. Git is one optional storage choice. Each task's formal authority and mutable Source still come from the adopter's configured task-type rules and must be revalidated before integration; the Git ref SHA is only the storage revision.

The remote must support writes to a dedicated `refs/heads/handoff-v1` namespace and the explicit expected SHA form of `--force-with-lease`. Limit writers to that namespace if the host supports it. Do not point the module at a general application source repository unless the adopter has explicitly designated its dedicated Handoff refs for storage. Configure authentication through the host's normal private credential mechanism; this module neither obtains nor stores credentials, and a protected or unavailable ref stops the Handoff mutation. No operation writes a regular source branch, Notion page, Jira issue, or another selected authority.

On Windows, full SHA-256 record refs under a deeply nested **local bare remote or writer clone** can exceed Git's default path capacity. A controlled local test showed that `core.longpaths=true` on both the isolated bare remote and each writer clone allowed that exact ref to be written and read back; an adopting user must verify the selected host's behavior and may instead use a shorter isolated Git store path. The module never changes Git configuration. A ref that remains absent after a rejected create-only push is an unverified storage write, not evidence of a competing revision. Only a different observed remote SHA is a conditional revision conflict. Preserve the Operation ID and inspect the selected remote's ref path, permissions, and long-ref support before retrying.

## Mapping

- `New-GitHandoffAdapter` takes `RepositoryRoot`, `RemoteName`, and a safe `RefPrefix`. The adopter must opt in and separately establish remote write permission; creation does not create the remote or Handoff data.
- A common Task Key and each exact peer Branch ID map to separate ref names containing full SHA-256 of UTF-8 logical identifiers. A branch record ID independently hashes the Task Key and Branch ID, so legal identifiers containing delimiters cannot alias another pair. A per-field event maps to a full SHA-256 of the composite Operation ID, Record ID, and Field identity. Stored JSON retains the original identifiers; readback rejects a ref with a different identity.
- `New-GitHandoffCommon` and `New-GitHandoffBranch` require the adopter's nonempty actual writer `Actor` and use create-only empty expected leases. Creation rejects an `Active Branches` field before writing because only the canonical common index reconciliation operation may change that structural value. `Set-GitHandoffFields` requires the exact revision returned by `Get-GitHandoffCommon` or `Get-GitHandoffBranch`, plus one stable Operation ID. One refspec per push implements a single-record conditional mutation. Re-read both the remote ref and the record after writing; a peer revision conflict is a stop and formal Source revalidation, never a blind replay.
- A committed record keeps the operation digest and every changed field. Each event uses its own immutable create-only ref; if an event push fails, retry the **same** operation ID and field keys. The adapter finds the operation's original first-parent commit, so a later peer edit of the same field cannot rewrite or erase the earlier event. A branch created without a successfully updated common Active index remains recoverable by its exact Branch ID; repeat its original operation to finish the index.
- For a Lifecycle, Work State, or Branch Outcome transition, supply a concrete `Reason` and a traceable `Actor` when calling `Set-GitHandoffFields`; the adapter rejects a transition without a reason. The event retains previous and new state, original operation time, Reason, Actor, Source from its record commit, structural or branch integration status, and verified readback. Retrying an already committed common index must also finish a pending per-field event before reporting the index complete.
- `Set-GitHandoffBranchLifecycle` archives one exact branch and conditionally removes its common index entry, or restores only that branch on explicit continuation and conditionally adds the index entry. A failed index write is a reported durable branch with a pending common step. Do not archive common while its Active index still contains any branch; archive changes Lifecycle alone and does not reset last material activity. The daily enumerator and inactivity scheduler remain separate SYP-217 work.

`Branch Outcome` is permitted only for branch records with an allowed value and an explicit `DecisionConfirmed` call after the Skill has verified the user's decision and common readback. This argument expresses an already-established Gate; it is not new authorization or independent proof. Preserve the decision Source and concrete Reason in the record and event. Configure the Git author identity in the isolated object store separately; an event Actor is supplied by the adopter's actual writer and must not be inferred from an unverified Git identity. If Git ref force-with-lease semantics, exact lookup, remote permission, or a signed release Gate is unavailable, report durable v1 saving as incomplete; do not fall back to last-write-wins Notion page writes.

## First fork from a common-only A conversation

Fix the pre-fork common revision, original A host identity and distinct A/B Branch IDs. Before creating branches, use `Set-GitHandoffFields` with the expected common revision and one stable operation ID to record a versioned, parseable `fork pending` payload in common Current; read that state back. The payload must retain the **exact** pre-fork A Current and Source, the independently verified confirmed Current/Source baseline, fork point, both IDs and all fixed operation IDs. A JSON string in the existing Current field is one valid mapping; its snapshot and baseline must remain recoverable when the previous common Current is replaced. This is structural metadata, not a selection of either candidate. A restarted writer reads the durable pending payload and exact A/B refs, validates the Task Key/revision/identities and resumes only missing steps with the same operation IDs; it must not recover A from the original process's memory or guess from an overwritten common Current. Incomplete or unverifiable payload keeps pending and stops branch creation. B starts from the confirmed shared baseline with its own Current/Source and a traceable fork reference. If authority cannot distinguish a fact from an A-only candidate, leave it in A and keep the fork pending.

Call `New-GitHandoffBranch` for the original A identity first, using the persisted A snapshot, then for B using the persisted verified shared baseline, with the **same** pre-fork revision as Fork Point, separate stable operation IDs, and each actual writer Actor. The module creates each branch ref with an empty expected lease, verifies its record/events, and conditionally indexes that exact Branch ID. Read back A and B, their Task Key/Fork Point/Current/Source, and both common Active index entries. Only then use one conditional `Set-GitHandoffFields` operation to write **both** common Current and Source as confirmed shared state with A/B provenance, clear pending, and read back both fields/events. The original A-only Source remains in A, not common. After that verified conversion, A and B may independently advance their own branches. If A already has a branch, revalidate it and create only B; do not create a duplicate A record. Before creating B, conditionally persist and read back a smaller pending reconciliation marker containing A's exact ID/revision, B's intended ID, fork point, verified index state, and stable B-create/index Operation IDs; clear it only after B and its index entry read back.

If a second branch or index write is uncertain, retain the original IDs and pending Current. A branch may exist by exact Branch ID while absent from common Active index; retry `New-GitHandoffBranch` with the **same** operation ID and fields to reconcile only its missing event/index step. A Task Key-only singleton lookup cannot treat a pending first fork as finished. Do not copy an unselected A candidate to B, promote it to common, write branch-only progress to common, or remove pending before both branch/index/common readbacks.

## Controlled test boundary

`tests/GitRefHandoffAdapter.Tests.ps1` uses an isolated local bare Git remote and separate writer clones. It covers duplicate common create, required creation actor, pre-write structural-index rejection, delimiter-safe record identity, stale common CAS, two peer branches, per-field event retry, record/event and branch/index partial failure, an already committed index with a pending event, later same-field edits, provenance, invalid states, exact archival/restore, and common protection. This is an implementation test, not an adopter's actual remote, cross-environment installation, or a trusted signed release receipt. For a live E2E, choose the storage remote, test two actual writer environments, record ref SHA and readbacks, and document rollback and permissions separately.
