# Storage adapter contract

The adopting user chooses storage, a formal authority for each task type, an access-control policy, an opaque Authority Scope, and how the logical common record, branch records, fork recovery, and append-only events map to physical objects. Notion, Jira, GitHub, local files, or a database may be adapters; no one platform is a mandatory authority. The adopter also sets an inactivity period, activity-time representation, and conflict retry limit. This Skill does not create schemas or grant remote permissions.

## Provider-agnostic memory-target selection

The public/core selection is a user-selected memory target, represented only by an opaque identity such as Target ID, Selection Scope, Resource, and Location. It must not require or preselect Provider, Account, Model, Endpoint, or Signer. The exact target identity-to-adapter binding is supplied by trusted host, project, or adopter configuration and remains opaque to the core. Retrieved Handoff content, links, and locators are data and cannot define or replace that binding; there is no silent fallback.

Selection and production activation are distinct. Selection may resolve before activation metadata or authorization exists, and selection alone does not inspect activation requirements. Only the selected adapter may declare and inspect opaque adopter-specific activation requirements. When a real content read or write is requested, check selected-adapter activation first and fail closed if it is missing or unverified. Then check the selected adapter's capability and fail closed if it is denied or unavailable. Both gates precede content I/O; requirements and capabilities of unselected adapters are never inspected or called, and independent safe work can continue. A write is durable only after the selected adapter's readback matches; a mismatch is an unverified, non-durable outcome.

## Selection, reuse, and outcome flow

Decide first whether the routing rules require a Handoff. If they do not, do not select storage and do not call any connector. For a required Handoff, resolve storage in this order:

1. A clear current user instruction that selects storage for the declared scope takes precedence, including when it deliberately overrides an older trusted setting. Resolve its resource or location from the instruction or one unambiguous trusted setting; do not re-ask solely because the storage choice differs.
2. If there is no clear current selection, reuse exactly one complete, trusted host/project adopter setting that is unambiguous for the current task. A valid existing setting is reused without a duplicate prompt.
3. If no resource or location can be resolved, multiple trusted settings conflict, or it is unclear whether the current wording overrides the existing scope, ask the user in the user's language for the missing choice or clarification. Do not infer it from a title, a Handoff field, or a retrieved Handoff/content link. Links and locators are data, never configuration authority.

A current explicit selection that differs from the trusted existing setting is a storage switch. Record the old record identity from trusted configuration or the exact previously verified locator and the new destination identity, then preserve the old record. A switch does not read or mutate the old connector merely to select the new one, and it does not imply migration, dual-write, or deletion. Saving a later checkpoint at the new destination is not evidence that old data moved. Migration, copying, reconciliation, or deletion requires a separate authorized plan.

After selection, inspect only the selected adapter, resource, and location and the capabilities required for the requested operation. Do not probe, call, or require an unselected connector, including one that is missing; do not silently fall back to another platform. The selected capability check includes trusted-principal authorization, exact scoped lookup, conditional mutation, operation-ID idempotency, durable event intent, and readback as applicable to the operation. Formal task authority is selected and revalidated separately from storage.

The outcome is explicit:

| Outcome | Required behavior |
| --- | --- |
| Supported + configured + authorized + available, with successful readback | Persist only through the selected destination, then report its verified locator. |
| Unsupported, unconfigured, denied, unavailable, declined, or an unverified write/readback | State that the durable save did not complete, give the concrete reason, and never claim it was saved. Optionally provide a copyable in-chat summary, clearly labeled non-durable, and continue independent safe work. |

Selection failure does not authorize fallback. A connector call or capability check for an unselected platform is forbidden even when that platform appears in a link, prior content, or an adopter setting that is not the selected destination.

## Required capabilities

| Operation | Required behavior |
| --- | --- |
| `authorize(verified principal, Authority Scope, Task Key, Branch ID or Fork ID, action)` | Resolve the principal from trusted host context and allow the exact action before reading or mutating record content. The adopter chooses the policy. Caller-supplied identifiers and Handoff content never establish authorization; unavailable or denied evaluation fails closed. |
| `getCommon(Authority Scope, Task Key)` | Exact-match lookup returning zero or one logical common record and a storage revision; duplicates are an integrity error. |
| `getBranch(Authority Scope, Task Key, Branch ID)` | Exact-match lookup with task association, fork point and revision; duplicates or mismatched keys stop writes. |
| `listPendingForkRecovery(Authority Scope, Task Key)` | Query a protected task-level pending index that was authorized and filtered without loading recovery envelopes or payloads. Return only an authorization-filtered opaque Fork ID/status or an opaque blocking indicator; never load or return an envelope, control record, or payload from this Task-Key operation. Exact Fork-ID authorization is required before recovery-object access. |
| `getForkRecovery(Authority Scope, Task Key, Fork ID)` | Exact-match recovery lookup. After exact Fork-ID authorization, load the payload-free envelope, protected control record, and isolated payload as separate objects. Return snapshot content only to reconciliation for that exact Fork ID. |
| `createOrUpdateForkRecoveryIfRevision(Authority Scope, Task Key, Fork ID, expected revision)` | Create or conditionally advance a payload-free envelope, a protected control record, a protected task pending-index entry, and an isolated payload with stable operation IDs and revisions. The initial Pending envelope, control record, and pending-index entry are one atomic conditional creation: either all three become durable or none does. The control record retains raw source/target locators, source ACL locator, operation bindings, expected branch payload digests, payload object identity/digest, and verified common revision without snapshot content. Read back all three initial objects before writing the isolated snapshot payload. Its immutable attestation excludes mutable recovery Status and terminal evidence on the outer recovery record, so completion does not rotate the snapshot digest. On completion, persist and read back the payload, release the common fence before or atomically with the terminal transition, then atomically mark both envelope and pending-index entry Completed and read back both. None is a common field, branch field, or common/branch field event. |
| `claimForkRecoveryTargetIfRevision(Authority Scope, Task Key, Fork ID, target Branch ID digest, creation Operation ID digest, expected envelope revision, expected common revision, payload attestation)` | After validating the isolated payload against its immutable object identity/digest and control record, conditionally store and read back a payload-free creation claim. The first claim atomically verifies or fences the exact common revision for both common-only and existing-branch forks. The claim and abandonment compete on the same envelope revision. |
| `createBoundForkBranchIfAbsent(Authority Scope, Task Key, Fork ID, Branch ID, Operation ID, expected envelope revision, payload attestation, common revision, proposed branch payload)` | Atomically prove the live claim, exact target-to-operation binding, verified payload attestation, expected common fence, and digest of the proposed Fork Point plus branch fields before creating the branch. Persist the Fork ID and creation Operation ID with the target. An unbound generic branch create is invalid for a fork target. |
| `abandonForkRecoveryIfRevision(Authority Scope, Task Key, Fork ID, expected revision)` | Using the protected control record, conditionally mark an envelope-only failure Abandoned only after exact authorization and durable proof that the isolated payload, every raw branch-creation target record, every corresponding creation outcome, and every target index entry are absent and the envelope has no creation claim. Atomically mark both envelope and pending-index entry Abandoned and read back both so normal recall stops treating the terminal recovery as Pending. A pre-existing source branch is not a creation target. An unverifiable check leaves it Pending. |
| `listActiveBranches(Authority Scope, Task Key)` | Read only the common record's indexed Active branches. A fresh conversation by itself does not call this operation. |
| `createIfAbsent(Authority Scope, Task Key, optional Branch ID or Fork ID)` | Enforce one common record per Authority Scope + Task Key, one branch per Authority Scope + Task Key + Branch ID, and one recovery envelope/control/payload set per Authority Scope + Task Key + Fork ID using a uniqueness constraint or equivalent atomic check. It may create a non-fork branch; every fork target uses `createBoundForkBranchIfAbsent`. |
| `stageEventIntentsIfAbsent(Authority Scope, Operation ID, Record ID)` | Before an exposed record mutation, durably store and read back one complete intent per changed field: event key, Verified Principal from trusted host context, previous/new state, reason, display Actor/time, Source/evidence, and integration result. An adapter may instead include the same intents atomically in the record commit. |
| `updateIfRevision(Authority Scope, expected revision, Operation ID, changed fields)` | Conditional update or ETag compare-and-swap; report a stale revision without overwriting another writer. Persist a stable operation ID so retrying uncertain results cannot double-write. |
| `appendEventIfAbsent(Authority Scope, Operation ID, Record ID, Field)` | Store immutable event identity and provenance per changed field, keyed by the scoped composite of operation, record, and field. Repeated calls return that field's existing event without dropping other fields of the same mutation. |
| `readback(Authority Scope, exact record identity)` | Re-read all intended record fields, association, revision and operation outcome before calling integration or archival successful. |
| `materialActivity(Authority Scope, exact record identity)` | Return latest semantic state change or explicit continuation. Use native last-edit metadata only if reads/no-ops/maintenance do not advance it; otherwise maintain a custom field. |

An adapter without trusted-principal authorization, scoped lookup, conditional mutation, operation-ID idempotency, and recoverable event intents is not suitable for concurrent peer branches. Authorize every lookup, list, creation, mutation, readback, event, and recovery operation against the exact action tuple before record content is loaded or exposed. Bind Authority Scope into physical identity and every logical common, branch, recovery, operation, and event record; knowing a Task Key, Branch ID, Fork ID, ref, URL, or record payload never permits access. Fork-recovery access must be at least as restrictive as its source branch. Fail closed for unauthorized Handoff reads and all unverifiable writes; local independent work can continue. Do not silently downgrade to last-write-wins. A platform that cannot atomically commit common and branch changes must preserve the fixed selection sequence and a retryable per-record operation log. After a selected, partially selected, or superseded branch is archived, the adapter conditionally removes that exact Branch ID from the common Active index with a stable operation ID and verifies both branch Lifecycle and index readback. Branch creation followed by common index update also needs a retryable step: an unindexed branch remains discoverable by its exact authorized Branch ID, is reported as partial, and cannot be considered fully available through scoped Task Key-only lookup until its common index readback succeeds. An Archived branch still present in the common Active index is a partial index failure: retain its archive and index operation IDs, reconcile the index conditionally, and do not archive common until that step reads back. Partial failure reports every committed, pending, and unverifiable action. A conditional conflict requires re-reading formal authority and the affected records before reapplying the Gate; do not blindly replay old candidate content.

Branch finalization after a user decision binds the exact common origin revision and a decision identity over its complete canonical field map. The common decision must also carry one binding per affected branch: exact Branch ID, reviewed origin revision, collision-resistant identity of the canonical reviewed content, Continuation Generation, and intended outcome. Before committing that decision, the adapter re-reads every branch and requires the exact reviewed revision, identity, and generation; a changed branch requires renewed user confirmation. Structural Active-branch index, material-activity metadata, and the operation log are excluded from the common identity. Lifecycle, Branch Outcome, material-activity metadata, and the operation log are excluded from reviewed branch content identity; Authority Scope, Continuation Generation, and every other identity, fork, state, source, candidate, applicability, and adopter-defined user-reviewable field are included. Before and after each outcome or decision-driven Lifecycle mutation, the adapter verifies both identities, the unchanged generation, and that current common and branch revisions descend from their bound origins. Only finalization and structural fields may advance the corresponding storage cursors, and the applied outcome must equal the branch binding. Beginning any explicit continuation of an existing branch increments Continuation Generation in one conditional operation before new work or a fork; it applies while Active and, when Archived, atomically sets Lifecycle Active too. One stable continuation Operation ID owns one increment across retries. This permanently invalidates every older branch binding even if other fields later match. Read-only inspection and finalization do not increment. Final readback proves both identities, generation, and current cursors. A changed decision field, reviewed branch content, or generation stops stale finalization, reports committed steps, and requires renewed confirmation; a branch-only compare-and-swap, an immutable common origin, or a content digest without its origin revision is insufficient.

For every creation or mutation, including a single-field Lifecycle, Work State, Source, or Active-branch-index change, compute the actual field changes and complete event intents before exposing the record change. The adapter must either include all intents atomically in the conditional record commit, or create and read back a separate write-ahead stage first. Each durable operation and intent contains the immutable Verified Principal resolved from trusted host context, stable Operation ID, Record ID, Field, Previous State, New State, Reason, display Actor, Time, Source/evidence, and Integration Result. Actor is a descriptive caller claim and never authorizes access or replaces Verified Principal. The later record revision and actual Readback Result are bound after readback; they are never guessed in advance. Read back each changed field and revision, append one immutable event per changed field from the durable intent using the composite event key, and read back the event identity before claiming the checkpoint complete. If the writer stops after the record commit, another authorized writer reconstructs every event from that original intent alone and preserves its original Verified Principal. Retain the stage until all event identities are verified. If record readback or event append/readback fails, retain the exact per-record operation, staged payload, and pending field event keys for reconciliation. Do not regenerate a new operation ID and repeat an uncertain write.

Every missing branch creation needs dedicated fork-recovery state before the branch write. Its payload-free envelope, protected control record, and isolated snapshot payload may share a physical service with Handoff records, but they use separate physical objects or logically isolated partitions, identities, conditional revisions, and recall boundaries. The control record contains the raw source and target locators, source ACL locator, exact Branch-ID-to-Operation-ID map, expected branch-creation payload digests, payload object identity/digest, and verified common revision needed for authorization, claims, creation, and abandonment; it contains no snapshot or shared baseline. Atomically create the initial Pending envelope, protected control record, and protected task pending-index entry with absent-value preconditions, then read back all three before the payload. A failed initial write leaves none of the three visible; once visible, the control record is always available for authorized abandonment and the pending index always blocks unsafe singleton resume. Complete and read back the payload first. Release any durable common fence before, or atomically with, the terminal step; then atomically mark the envelope and pending-index entry terminal and read back both. A terminal index entry remains auditable but cannot block normal recall. Snapshot content never appears in the envelope, control record, common or branch fields, or their append-only field-event history. A normal Task Key resume queries the protected task pending index without loading envelope, control, or payload objects. That index returns only Fork IDs already filtered by the adopter's task/source-branch authorization policy, or only an opaque blocking indicator when identifiers cannot safely be exposed. Only reconciliation authorized for the exact Fork ID may load the envelope and control record, and only that flow may read the payload. Any recovery audit history keeps the same isolated access boundary and never copies payloads into common/branch events.

The envelope retains only payload-free evidence needed to detect and coordinate incomplete creation: scoped identity, payload digest, the exact common revision verified at creation, identity digests for absent target branches and their stable creation operations, an exact target-digest-to-operation-digest binding, per-target creation claims, creation principal and timing. `Branch Creation Operations` in the isolated payload and protected control record maps every absent target Branch ID to exactly one stable creation Operation ID with no missing or extra target. Each target also has a digest of its expected canonical creation payload, including Fork Point and all branch fields. For a common-only first fork, Fork Point equals the exact common revision used to verify the empty Active index. Existing-branch forks record the exact post-continuation common revision under the same fence. Re-read that revision after envelope/control creation and before an absent payload write. A drift leaves the recovery Pending and non-claimable.

Before the first target claim, validate the isolated payload bytes and canonical content against the protected payload object identity/digest and every envelope/control binding. The claim compare-and-swap atomically verifies the exact live common revision or acquires an equivalent common-record fence that prevents semantic or decision changes until every target create and structural common conversion completes. Apply this same gate to common-only and existing-branch forks; if common changed, release or refuse the fence, re-read formal authority, and reapply the integration gate before any branch is created. Every later claim verifies that the fence remains valid. After the claim, `createBoundForkBranchIfAbsent` atomically verifies the live claim, Fork ID, exact target/Operation binding, envelope revision, payload attestation, common fence, and digest of the proposed creation payload, then persists the Fork ID and creation Operation ID with the new branch. A generic create cannot create a fork target, and a mismatched target, operation, Fork Point, or field set fails before any durable branch write.

If the payload never becomes durable, an authorized reconciliation loads the protected control record and may conditionally change the envelope from Pending to Abandoned. It proves by exact scoped reads using the raw protected target/operation locators that the payload is absent, every branch-creation target record is absent, no matching target Branch ID is present in the common Active index, no target creation outcome is durable, and no creation claim exists. The final Abandoned envelope and pending-index mutation is one atomic conditional operation, and every creation claim compares and swaps the same envelope revision, preventing a target write from starting between the absence checks and terminal transition. Read back both terminal objects; a terminal index is ignored by normal Pending recall. A pre-existing source branch is excluded from the target set. If any target object or claim exists, any identity cannot be checked, or authorization/evidence is unavailable, the envelope remains Pending. The Abandoned update records a stable abandonment Operation ID, immutable Verified Principal, reason, and time, is read back, and stays audit-readable. Abandoned envelopes do not block singleton resume, cannot be completed, and cannot be reused to create a payload or branch; a later attempt uses a new Fork ID.

For the first fork of a common-only conversation, the recovery set contains the original host identity, one stable fork point equal to the verified pre-fork common revision, intended source/new peer IDs, exact Branch-ID-to-creation-Operation-ID and expected-payload-digest maps, other per-record Operation IDs, a lossless snapshot of the original A Current and Source, and an independently verified shared Current and Source baseline. Create and read back the original A branch from the attested pre-fork payload, then the alternative B branch from the attested confirmed baseline. If A already exists, first begin A's explicit continuation and read back its incremented generation; then record the exact current common revision as the recovery fence and persist A's exact post-fence Branch ID/revision/generation, lossless Current and Source snapshot, verified shared Current and Source baseline, intended B ID, fork point, verified Active index, exact B-to-create-Operation binding and expected payload digest, plus stable continuation/index Operation IDs. Before B's claim, require that exact common revision or an equivalent decision-identity fence and reapply the integration gate if it changed. If A advances after the recovery is durable, verify its exact Task Key/Branch ID, preserve its newer state, and create B only from the attested shared baseline; no historical-revision read capability is assumed. Mark recovery Completed only after every new branch and its index entry read back and after the common fence is safely released. An interrupted writer recovers from the exact durable recovery set and exact Handoff records, never from lost session memory; a missing or unverifiable snapshot, baseline, identity association, attestation, operation binding, common fence, or index state blocks writes. A partial fork can have one indexed branch; the pending index prevents Task Key-only lookup from misidentifying that singleton as a completed peer fork. Only exact Branch ID lookup and idempotent step reconciliation are safe until final common readback. No candidate choice is implied by structural conversion.

## Mapping and identity

Required common fields are Authority Scope, Task Key, Intent, Scope, Current, Source, Lifecycle, and Work State. Required branch fields are Authority Scope, Task Key, Branch ID, Fork Point, Continuation Generation, Current, Source, Lifecycle, and Work State. Continuation Generation starts at `0` and increments once for every explicit continuation of that existing branch, before resumed work or a new fork; an Archived-to-Active restoration shares the same conditional operation. A fork-recovery record requires Authority Scope, Task Key, Fork ID, Fork Point, and mutable status, while its immutable snapshot payload requires the source and intended branch identities, isolated source snapshot, shared baseline, verified Active index, exact Branch Creation Operations map, and other step Operation IDs; mutable recovery status and terminal evidence are excluded from that payload attestation; its separate envelope contains only scoped identity, status, payload digest, verified common revision at creation, branch-creation target/operation identity digests and their exact binding, claims, operation, principal, and timing evidence. Recovery status is Pending, Completed, or Abandoned; Abandoned is allowed only for the verified envelope-only failure path above. Common may also store Active Branches, baselines, Conflict, Keep Active Until, and Last Activity At. Branch may store candidate conclusions, Branch Outcome, Keep Active Until and activity. Every event binds Authority Scope and Verified Principal; event fields and allowed states are in `task-handoff-contract.json`. Branch Outcome remains empty before a user decision; `Conflict` is a common marker, not Lifecycle.

Authority Scope is a stable opaque authorization and physical-identity namespace chosen by the adopter; it is not a platform mandate, tenant name, or credential. Task Key is unique only within that scope, not a title. Authority Scope is an explicit logical component of every lookup, list, create, update, event, recovery, uniqueness, and readback key even when an adapter supplies it through immutable bound configuration rather than a separate call argument. Physical identities derived from multiple logical components must use an unambiguous encoding such as length-prefixing, structured canonical encoding, or independently hashed fixed-width components; delimiter concatenation alone is insufficient because a legal component may contain the delimiter. Every fork inherits the parent's Authority Scope and Task Key, including when the key came from the origin host task rather than formal work. Branch ID is stable host identity or a generated ID recoverable independently from host metadata, not a transient chat-only label. Operation ID is stable for one logical mutation across retries, distinct from the record ID and branch ID. The storage revision is opaque and obtained fresh on every authorized read. A source revision such as a Git commit belongs inside Source and is revalidated separately from storage revision. Record links must round-trip from branch to its one scoped common record. An optional branch Applicability Scope captures the exact version, environment, and Scope under which verified claims hold; it does not change global Scope or required common fields. Structural common index changes on fork, archive, and exact restore cannot promote branch decisions or unverified facts.

If exact lookup or activity semantics cannot be implemented on the chosen platform, mark that adapter as unavailable and explain the missing capability. A legacy adapter may support exact read-only mapping while new writes use the v1 logical model; it does not run a bulk migration or scan all history. Never save credentials or unapproved sensitive material in any physical mapping.
