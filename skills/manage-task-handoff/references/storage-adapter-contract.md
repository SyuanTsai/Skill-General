# Storage adapter contract

The adopting user chooses storage, a formal authority for each task type, an access-control policy, an opaque Authority Scope, and how the logical common record, branch records, fork recovery, and append-only events map to physical objects. Notion, Jira, GitHub, local files, or a database may be adapters; no one platform is a mandatory authority. The adopter also sets an inactivity period, activity-time representation, and conflict retry limit. This Skill does not create schemas or grant remote permissions.

## Required capabilities

| Operation | Required behavior |
| --- | --- |
| `authorize(verified principal, Authority Scope, Task Key, Branch ID or Fork ID, action)` | Resolve the principal from trusted host context and allow the exact action before reading or mutating record content. The adopter chooses the policy. Caller-supplied identifiers and Handoff content never establish authorization; unavailable or denied evaluation fails closed. |
| `getCommon(Task Key)` | Exact-match lookup returning zero or one logical common record and a storage revision; duplicates are an integrity error. |
| `getBranch(Task Key, Branch ID)` | Exact-match lookup with task association, fork point and revision; duplicates or mismatched keys stop writes. |
| `listPendingForkRecovery(Task Key)` | Return only pending Fork IDs and status envelopes needed to block unsafe singleton auto-resume; do not return branch snapshots. |
| `getForkRecovery(Task Key, Fork ID)` | Exact-match recovery lookup. Return its isolated payload only to the reconciliation flow for that exact Fork ID. |
| `createOrUpdateForkRecoveryIfRevision` | Create or conditionally advance the dedicated logical recovery record with stable operation IDs and its own revision. It is not a common field, branch field, or common/branch field event. |
| `listActiveBranches(Task Key)` | Read only the common record's indexed Active branches. A fresh conversation by itself does not call this operation. |
| `createIfAbsent` | Enforce one common record per key and one branch per Task Key + Branch ID using a uniqueness constraint or equivalent atomic check. |
| `stageEventIntentsIfAbsent(Operation ID, Record ID)` | Before an exposed record mutation, durably store and read back one complete intent per changed field: event key, previous/new state, reason, actor/time, Source/evidence, and integration result. An adapter may instead include the same intents atomically in the record commit. |
| `updateIfRevision(expected revision, Operation ID, changed fields)` | Conditional update or ETag compare-and-swap; report a stale revision without overwriting another writer. Persist a stable operation ID so retrying uncertain results cannot double-write. |
| `appendEventIfAbsent(Operation ID, Record ID, Field)` | Store immutable event identity and provenance per changed field, keyed by the composite of operation, record, and field. Repeated calls return that field's existing event without dropping other fields of the same mutation. |
| `readback` | Re-read all intended record fields, association, revision and operation outcome before calling integration or archival successful. |
| `materialActivity` | Return latest semantic state change or explicit restore. Use native last-edit metadata only if reads/no-ops/maintenance do not advance it; otherwise maintain a custom field. |

An adapter without trusted-principal authorization, scoped lookup, conditional mutation, operation-ID idempotency, and recoverable event intents is not suitable for concurrent peer branches. Authorize every lookup, list, creation, mutation, readback, event, and recovery operation against the exact action tuple before record content is loaded or exposed. Bind Authority Scope into physical identity and every logical common, branch, recovery, operation, and event record; knowing a Task Key, Branch ID, Fork ID, ref, URL, or record payload never permits access. Fork-recovery access must be at least as restrictive as its source branch. Fail closed for unauthorized Handoff reads and all unverifiable writes; local independent work can continue. Do not silently downgrade to last-write-wins. A platform that cannot atomically commit common and branch changes must preserve the fixed selection sequence and a retryable per-record operation log. After a selected, partially selected, or superseded branch is archived, the adapter conditionally removes that exact Branch ID from the common Active index with a stable operation ID and verifies both branch Lifecycle and index readback. Branch creation followed by common index update also needs a retryable step: an unindexed branch remains discoverable by its exact authorized Branch ID, is reported as partial, and cannot be considered fully available through scoped Task Key-only lookup until its common index readback succeeds. An Archived branch still present in the common Active index is a partial index failure: retain its archive and index operation IDs, reconcile the index conditionally, and do not archive common until that step reads back. Partial failure reports every committed, pending, and unverifiable action. A conditional conflict requires re-reading formal authority and the affected records before reapplying the Gate; do not blindly replay old candidate content.

Branch finalization after a user decision binds the exact common origin revision and a decision identity over its complete canonical field map. The common decision must also carry one binding per affected branch: exact Branch ID, reviewed origin revision, collision-resistant identity of the canonical reviewed content, Continuation Generation, and intended outcome. Before committing that decision, the adapter re-reads every branch and requires the exact reviewed revision, identity, and generation; a changed branch requires renewed user confirmation. Structural Active-branch index, material-activity metadata, and the operation log are excluded from the common identity. Lifecycle, Branch Outcome, material-activity metadata, and the operation log are excluded from reviewed branch content identity; Authority Scope, Continuation Generation, and every other identity, fork, state, source, candidate, applicability, and adopter-defined user-reviewable field are included. Before and after each outcome or decision-driven Lifecycle mutation, the adapter verifies both identities, the unchanged generation, and that current common and branch revisions descend from their bound origins. Only finalization and structural fields may advance the corresponding storage cursors, and the applied outcome must equal the branch binding. An explicit restore increments Continuation Generation in the same conditional operation that sets Lifecycle Active; this permanently invalidates every older branch binding even if other fields later match. Final readback proves both identities, generation, and current cursors. A changed decision field, reviewed branch content, or generation stops stale finalization, reports committed steps, and requires renewed confirmation; a branch-only compare-and-swap, an immutable common origin, or a content digest without its origin revision is insufficient.

For every creation or mutation, including a single-field Lifecycle, Work State, Source, or Active-branch-index change, compute the actual field changes and complete event intents before exposing the record change. The adapter must either include all intents atomically in the conditional record commit, or create and read back a separate write-ahead stage first. Each durable intent contains the stable Operation ID, Record ID, Field, Previous State, New State, Reason, Actor, Time, Source/evidence, and Integration Result. The later record revision and actual Readback Result are bound after readback; they are never guessed in advance. Read back each changed field and revision, append one immutable event per changed field from the durable intent using the composite event key, and read back the event identity before claiming the checkpoint complete. If the writer stops after the record commit, another writer must reconstruct every event from the durable intent alone. Retain the stage until all event identities are verified. If record readback or event append/readback fails, retain the exact per-record operation, staged payload, and pending field event keys for reconciliation. Do not regenerate a new operation ID and repeat an uncertain write.

Every missing branch creation needs a dedicated logical fork-recovery record before the branch write. It may share a physical service with Handoff records, but it must use a separate object or partition, identity, conditional revision, and recall boundary. Its payload never appears in common or branch fields, nor in their append-only field-event history. A normal Task Key resume may list only pending Fork ID/status envelopes so it can block unsafe singleton auto-resume; only reconciliation for the exact Fork ID may read the snapshot payload. Any recovery audit history must keep the same isolated access boundary and must not copy payloads into common/branch events.

For the first fork of a common-only conversation, the recovery record contains the original host identity, one stable fork point and pre-fork revision, intended source/new peer IDs, per-record Operation IDs, a lossless snapshot of the original A Current/Source, and an independently verified shared Current/Source baseline. Create and read back the original A branch with its pre-fork Current/Source, then the alternative B branch with only the confirmed shared baseline and its own Current/Source. If A already exists, reuse it and persist a smaller recovery record containing A's exact Branch ID/revision, a lossless copy of A's Current/Source at the fork, the independently verified shared Current/Source baseline, the intended B ID, fork point, verified Active index, and stable B-create/index Operation IDs. If A advances after that record is durable, verify its exact Task Key/Branch ID, preserve its newer state, and create B from the persisted shared baseline; no historical-revision read capability is assumed. Mark recovery Completed only after every new branch and its index entry read back. An interrupted writer recovers from the exact durable recovery record and exact Handoff records, never from lost session memory; a missing or unverifiable snapshot, baseline, identity association, or index state blocks writes. A partial fork can have one indexed branch; the pending envelope prevents Task Key-only lookup from misidentifying that singleton as a completed peer fork. Only exact Branch ID lookup and idempotent step reconciliation are safe until final common readback. No candidate choice is implied by structural conversion.

## Mapping and identity

Required common fields are Authority Scope, Task Key, Intent, Scope, Current, Source, Lifecycle, and Work State. Required branch fields are Authority Scope, Task Key, Branch ID, Fork Point, Continuation Generation, Current, Source, Lifecycle, and Work State. Continuation Generation starts at `0` and changes only by incrementing once in the same conditional operation that explicitly restores an Archived branch. A fork-recovery record requires Authority Scope, Task Key, Fork ID, Fork Point, status, source and intended branch identities, the isolated source snapshot and shared baseline, verified Active index, and step Operation IDs. Common may also store Active Branches, baselines, Conflict, Keep Active Until, and Last Activity At. Branch may store candidate conclusions, Branch Outcome, Keep Active Until and activity. Every event binds Authority Scope; event fields and allowed states are in `task-handoff-contract.json`. Branch Outcome remains empty before a user decision; `Conflict` is a common marker, not Lifecycle.

Authority Scope is a stable opaque authorization and physical-identity namespace chosen by the adopter; it is not a platform mandate, tenant name, or credential. Task Key is unique within that scope, not a title. Every fork inherits the parent's Authority Scope and Task Key, including when the key came from the origin host task rather than formal work. Branch ID is stable host identity or a generated ID recoverable independently from host metadata, not a transient chat-only label. Operation ID is stable for one logical mutation across retries, distinct from the record ID and branch ID. The storage revision is opaque and obtained fresh on every authorized read. A source revision such as a Git commit belongs inside Source and is revalidated separately from storage revision. Record links must round-trip from branch to its one scoped common record. An optional branch Applicability Scope captures the exact version, environment, and Scope under which verified claims hold; it does not change global Scope or required common fields. Structural common index changes on fork, archive, and exact restore cannot promote branch decisions or unverified facts.

If exact lookup or activity semantics cannot be implemented on the chosen platform, mark that adapter as unavailable and explain the missing capability. A legacy adapter may support exact read-only mapping while new writes use the v1 logical model; it does not run a bulk migration or scan all history. Never save credentials or unapproved sensitive material in any physical mapping.
