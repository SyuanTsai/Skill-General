# Handoff operations

Read the machine-readable contract first. These steps govern task-local state; they do not choose a durable-memory system or authorize a new external operation.

## Create or resume

1. Obtain the adopter-defined opaque Authority Scope and a stable Task Key: an exact external work key such as `jira:ABC-1`, or the origin host task identity when no formal key exists. Resolve the verified principal from trusted host context and authorize the exact scope, task, optional branch or fork, and action before every lookup or mutation. Task Key, Branch ID, Fork ID, and Handoff content are resource locators, never proof of access. A new forked conversation inherits its parent's exact scoped Task Key; use its own conversation identity only for Branch ID. Avoid titles, topic similarity, and invented aliases. On explicit continuation, query the configured storage by exact Authority Scope and Task Key. No automatic scan on a new conversation.
2. Zero common matches allows one creation when the trigger and unique key are established. One match is reused. More than one stops all writes. Preserve duplicates and report their IDs. An archived common record is restored only for explicit continuation of that same Task Key.
3. Build the required common fields from the user request and verified sources, including the exact Authority Scope supplied by trusted adapter configuration. `Intent` states desired outcome and current phase. `Scope` marks clauses Active, Superseded, or Deferred and records constraints and authorization without inventing it. `Current` states focus, material changes, last successful check, unresolved work, and next safe action. `Source` distinguishes formal authority from working copies and includes mutable version, environment, revision, worktree, and their required revalidation. Lifecycle and Work State remain separate.
4. If an A conversation forks B and A already has a branch record, begin A's explicit continuation first with a stable Operation ID: conditionally increment Continuation Generation even when A is already Active, restore Lifecycle in that same operation if Archived, and read back the resulting exact revision and generation before taking the fork snapshot. This fence invalidates every earlier reviewed binding before B can be created. Fix that post-fence A revision as the fork point, then create only the missing B branch. Before that create, conditionally create and read back dedicated fork-recovery state that binds the existing A, a lossless snapshot of A's exact Current and Source at that revision, an independently verified shared Current and Source baseline, intended B, verified Active-branch index, stable continuation, B-create, and index-update Operation IDs. The payload-free envelope and isolated snapshot payload have separate physical objects or logically isolated partitions, identities, revisions, and recall boundaries. Common, branch, and append-only field-event records must never contain the payload. Normal task recall lists and loads only Pending envelopes to block singleton auto-resume; only exact fork reconciliation may read the snapshot payload. If A has only the common record, fix the pre-fork common revision, A's recoverable host identity, a stable fork point, and distinct A/B Branch IDs before any write. Classify A's pre-fork Current and Source: keep confirmed task-level facts as the shared baseline, but put A-only progress, hypotheses, and candidate conclusions in A's new branch; B starts from that confirmed baseline with its own Current and Source, retaining a traceable reference to the fork snapshot rather than treating A's candidate as selected. If the classification cannot be verified, keep the disputed fact in A and leave recovery Pending instead of promoting it to common. Both peer branches inherit the same Task Key, confirmed Intent, and Scope; neither is the task-level main.
5. Before every missing branch creation, conditionally create or resume its dedicated fork-recovery state using the exact Authority Scope, Task Key, and Fork ID as its logical identity. Persist and read back the payload-free Pending envelope first, then persist and read back the isolated payload. The payload maps every absent target Branch ID to exactly one stable creation Operation ID with no missing or extra target. The envelope carries scoped identity, payload digest, the exact common revision verified at creation, identity digests for branches that were absent and targeted for creation, stable branch-creation operation identity digests, their exact target-to-operation binding, payload-free per-target creation claims, and creation principal/time, but no snapshot or baseline. For a common-only fork, require Fork Point to equal the common revision used to verify the empty Active index. Re-read that common revision after the create-only envelope write and before writing a still-absent payload on retry; drift leaves the envelope Pending without a payload. After payload readback and before each target branch write, conditionally add and read back a claim only for the Operation ID bound to that exact target, together with immutable Verified Principal and time. If payload creation fails, the Pending envelope remains visible without exposing or requiring the payload. An exact authorized reconciliation may mark that envelope Abandoned only after scoped reads prove the payload, all branch-creation target records and creation outcomes, and all target Active-index entries are absent and the envelope has no creation claim. The Abandoned mutation and target claims compare and swap the same envelope revision; a concurrent claim wins or abandonment wins, never both. A pre-existing source branch in the verified Active index is not a creation target and does not prevent safe abandonment. Record and read back a stable abandonment Operation ID, immutable Verified Principal, reason, and time. If any check is unavailable or finds a durable target step or claim, leave the envelope Pending. Abandoned envelopes do not block singleton resume and cannot be completed or reused; retry with a new Fork ID. For a common-only first fork, the payload must include the intended A/B IDs, original A host identity, pre-fork revision and exact A Current/Source, independently verified shared Current/Source baseline, exact A/B Branch Creation Operations mapping, other stable per-record Operation IDs, and Pending status. Create A from that persisted pre-fork snapshot first, then B from the verified shared baseline, using separate create-if-absent operations and the same fork point. When A already exists, first complete and read back its stable continuation Operation ID; the smaller recovery payload must include A's exact post-fence Branch ID, revision, and generation, its lossless Current/Source snapshot at the fork, the verified shared Current/Source baseline, intended B ID, fork point, verified index state, an exact B-to-create-Operation binding, other continuation/index-update Operation IDs, and Pending status. Read back each new record, association, operation outcome, and the common Active-branch index; conditionally add only missing IDs if another peer advanced the index. For an existing-A fork, update and read back the payload as Completed only after the new branch and its index entry read back, then mark and read back the envelope Completed last. For a common-only conversion, keep the envelope Pending while conditionally setting common Current and Source to only confirmed shared state with fork provenance and the peer index; verify both fields and their events, then complete payload and envelope before either branch writes divergent work. A-only Source remains in A and in the isolated recovery payload, not common or common event history. This structural conversion does not select A or B or authorize a direction change.
6. After interruption, reconstruct every pending fork or missing-branch reconciliation only from the exact durable fork-recovery record, current common revision, and exact A/B branch lookups, all keyed by the same Authority Scope; never rely on the original writer's memory, a conversation summary, historical-revision lookup that the adapter did not declare, or a guessed overwritten Current. Missing or unverifiable A snapshot, shared baseline, identity association, or index state keeps recovery Pending and stops branch creation. If existing A advanced after the pending write, retain its newer state and use the durable fork-time snapshot only to verify provenance and preserve the fork point; create B from the persisted shared baseline. An A, B, event, index, or final common readback failure keeps the stable IDs, Operation IDs, and Pending status. Preserve every committed step, report the exact record and Operation ID still missing, and retry only that step; never write A-only changes into common or a peer branch. A branch whose index integration failed remains discoverable only by its exact Branch ID until reconciliation. Do not call the two-peer fork complete or let scoped Task Key-only lookup auto-resume a lone indexed branch while any recovery envelope is Pending.
7. With Branch ID, exact scoped lookup must return at most one authorized matching branch linked to that Task Key. With only Task Key, read the authorized common Active-branch index. A single Active branch can be resumed only when no fork is pending. For several branches use thread identity or unique request context; ask for a direction only when neither identifies the branch and that ambiguity is material. Before new work or a new fork, begin an explicit continuation of the exact existing branch with one stable Operation ID. Increment Continuation Generation in one conditional branch operation whether the branch is Active or Archived; if Archived, restore the common record for the same scoped key first if needed and change that branch's Lifecycle to Active in the same generation operation. Read back Lifecycle and generation before work proceeds, and conditionally add a restored branch to the common Active index. The generation change invalidates every earlier reviewed-branch binding before resumed or forked work can race with finalization. Retrying the same continuation Operation ID must prove and complete the same single increment; a later explicit continuation uses a new ID. If a step fails, retain its exact operation ID and report partial continuation; never present an unindexed branch in a Task Key-only lookup. Read-only inspection and finalization do not increment generation or reactivate an Archived branch.

## Checkpoint and integrate

1. Re-read the applicable formal source and mutable revision on resume. Treat a stored Source locator as an instruction to revalidate, never as automatic authority. Distinguish confirmed requirement from a branch proposal or unverified inference.
2. Compute only material differences for the target common or branch fields. A read, a new conversation, or a no-op write must not change Last Activity At. If the platform's native last-edit time advances on a no-op, the adapter must skip that write; if it advances on maintenance, use a custom material-activity field instead.
3. Before the conditional record write, build one complete event intent per changed field with composite Operation ID, Record ID, and Field identity, immutable Verified Principal from trusted host context, previous and new state, caller-supplied display Actor/time, reason, Source/evidence, and integration status. Actor is descriptive and is never authorization evidence. Either atomically commit the record and all intents in one compare-and-swap, or write the intents to a durable operation stage and read them back before mutating the record. Then read back each changed field and revision, append one immutable event per field from the durable intent with its verified or unresolved readback result, and read back every event identity before calling the checkpoint complete. Never erase older transitions. A retry of the same operation loads the first durable intent and write outcome without duplicating field events or changing its Verified Principal. If a record or event readback fails, preserve the exact operation, staged payload, and pending field keys for reconciliation instead of relying on lost process memory or inventing success.
4. An independently verified fact with a traceable Source and no task-direction effect can be integrated to common automatically. Preserve the originating Branch ID and applicability conditions. Candidate architectures, tradeoffs, selection/rejection/combination, Intent, global Scope, and authorization require user confirmation. Both branches may be Awaiting Review while common still has no selected outcome.
5. For mutually exclusive verified facts, compare actual version, environment, Scope, verification time and method. Record the applicability conditions in the branch's optional Applicability Scope and Source before integration. Revalidate against the adopter's authority source and current work state. Mark an outdated claim Superseded with a reason; keep results from distinct conditions with their applicability. If the same conditions still conflict and the decision is material, record Conflict with both provenances and safe stop; do not use last-write-wins or call it selected.
6. A revision conflict means the peer changed state after the read. Re-read the common, branches and formal source, reapply the integration Gate, then attempt a new conditional update only if valid. Limit retries according to the adapter. If authority is unavailable, keep facts in the branch as unverified and state which common integration was not done.

## Select, interrupt, archive

After explicit user selection, bind every affected Branch ID to the exact revision, canonical content identity, and Continuation Generation the user reviewed, plus its intended selected, partially selected, or superseded outcome. Re-read each branch immediately before the common write and require the exact reviewed revision, content identity, and generation; if a branch advanced, stop and obtain renewed confirmation. Write those branch bindings inside the common decision conditionally, then read it back and bind its origin revision plus a decision identity over the complete canonical common field map. Exclude structural `Active Branches`, material-activity metadata, and the operation log from the common identity. The reviewed branch content identity includes Authority Scope, identity, fork point, Continuation Generation, Current, Source, Work State, candidate conclusion, applicability, and all other user-reviewable fields while excluding only Lifecycle, Branch Outcome, material-activity metadata, and the operation log. Before and after every related Branch Outcome or Lifecycle mutation, re-read common and the exact branch. Require the same common decision identity and require the branch revision to equal or descend from its reviewed origin while preserving reviewed content and Continuation Generation; only verified finalization fields may advance its storage revision. Apply only the outcome stored in the common branch binding. A changed common identity, reviewed branch content, or Continuation Generation stops stale finalization and requires renewed user confirmation; retain already written steps as partial reconciliation instead of applying the old choice to newer or explicitly continued content. With both identities still bound, append each outcome and its reason/Source, then archive adopted and rejected source branches unless the user explicitly requests continued exploration. For each branch that becomes Archived, read back and bind the exact archived branch revision and generation, then conditionally remove only its exact Branch ID from the common Active index using a stable operation ID. Use the latest verified common and branch storage revisions as compare-and-swap cursors and advance them only after readback. After the index mutation, read common and branch/index states again: success requires the original common decision identity and reviewed branch content identity on verified descendant revisions with the bound generation, plus either the same bound Archived revision with the ID absent, or a concurrently restored Active revision with an incremented generation and the ID present. If restoration won the race, the old decision is invalid; cancel its stale removal and conditionally re-add a missing ID before reporting partial reconciliation. For a combined solution, record each branch's adopted portion in its binding before archiving. If a common write or readback fails, do not set outcomes or archive related branches. If either identity or the generation changes, or an outcome, archive, index update, compensation, or readback fails, retain the common decision origin and identity, all reviewed branch origins and content identities, latest verified storage revisions, records, and operation IDs; leave the operation as partial reconciliation. An Archived branch still present in the Active index continues to protect the common record and must not be presented as active.

On interruption, save focus, last success, external changes, blocker/failure, non-repeatable operations and next safe step, using Work State `Interrupted`, `Blocked`, or `Failed` as appropriate. Ready implementation uses `Awaiting Review`, never `Completed`. An explicit user close can archive immediately after safe state and readback are stored.

At Last Activity At plus the configured inactivity period (seven days by default), archive an expired branch by changing Lifecycle only. Read back and bind the exact archived branch revision and Continuation Generation before conditionally removing its ID from the common Active index. Immediately before every removal or retry, re-read that branch: if its Lifecycle, revision, or generation no longer matches the bound Archived state, cancel the stale removal. After any removal, re-read both records; if explicit continuation restored the branch to Active and incremented its generation during the race, invalidate any earlier decision binding, conditionally re-add a missing ID, and verify Active-plus-indexed state. If the index update or compensation fails, keep the Branch ID and stable operation IDs as a partial reconciliation job; the common remains protected until readback proves the lifecycle/index invariant. A future Keep Active Until protects it. Compute common activity as the maximum of its own material activity and each Active branch's material activity; any Active branch also prevents automatic common archival. Archive expired branches and verify index changes before evaluating whether common can be archived. Explicit continuation of an archived branch restores its common record if needed and only that exact branch; restoring common never restores every branch. The scheduler that enumerates records and enforces this policy is a separate task. Legacy records are left alone unless an exact scoped Task Key is explicitly resumed.
