# Handoff operations

Read the machine-readable contract first. These steps govern task-local state; they do not choose a durable-memory system or authorize a new external operation.

## Create or resume

1. Obtain a stable Task Key: an exact external work key such as `jira:ABC-1`, or the host task identity when no formal key exists. Avoid titles, topic similarity, and invented aliases. On explicit continuation, query the configured storage by exact Task Key. No automatic scan on a new conversation.
2. Zero common matches allows one creation when the trigger and unique key are established. One match is reused. More than one stops all writes. Preserve duplicates and report their IDs. An archived common record is restored only for explicit continuation of that same Task Key.
3. Build the seven required common fields from the user request and verified sources. `Intent` states desired outcome and current phase. `Scope` marks clauses Active, Superseded, or Deferred and records constraints and authorization without inventing it. `Current` states focus, material changes, last successful check, unresolved work, and next safe action. `Source` distinguishes formal authority from working copies and includes mutable version, environment, revision, worktree, and their required revalidation. Lifecycle and Work State remain separate.
4. If a fork occurs, create a stable Branch ID from host thread identity or a system-generated identifier, point it to Task Key and the shared fork baseline, then conditionally add it to the common Active-branch index and verify both readbacks. A and B can both be active. If a peer changed the common index, re-read and add only the missing ID; never replace the entire peer index. If branch creation succeeds but index integration fails, retain the exact branch ID and operation ID, report the unindexed branch, and retry that index step before treating Task Key-only lookup as complete. Branches inherit shared confirmed Intent and Scope at the fork; subsequent Current, Source, checks, hypotheses, outcomes, activity, and Work State belong to their own records. Do not overwrite common or a peer branch for a branch-only update.
5. With Branch ID, exact lookup must return at most one matching branch linked to that Task Key. With only Task Key, read the common Active-branch index. A single Active branch can be resumed. For several branches use thread identity or unique request context; ask for a direction only when neither identifies the branch and that ambiguity is material. Do not reactivate an Archived branch for read-only inspection.

## Checkpoint and integrate

1. Re-read the applicable formal source and mutable revision on resume. Treat a stored Source locator as an instruction to revalidate, never as automatic authority. Distinguish confirmed requirement from a branch proposal or unverified inference.
2. Compute only material differences for the target common or branch fields. A read, a new conversation, or a no-op write must not change Last Activity At. If the platform's native last-edit time advances on a no-op, the adapter must skip that write; if it advances on maintenance, use a custom material-activity field instead.
3. Append a change event for an actual state transition, with operation ID, record and field identity, previous and new state, actor/time, reason, Source/evidence, integration status, and readback result. Never erase older transitions. Use the adapter's conditional write with expected revision/ETag and a stable operation ID; a retry of the same operation returns the first outcome without duplicating changes.
4. An independently verified fact with a traceable Source and no task-direction effect can be integrated to common automatically. Preserve the originating Branch ID and applicability conditions. Candidate architectures, tradeoffs, selection/rejection/combination, Intent, global Scope, and authorization require user confirmation. Both branches may be Awaiting Review while common still has no selected outcome.
5. For mutually exclusive verified facts, compare actual version, environment, Scope, verification time and method. Revalidate against the adopter's authority source and current work state. Mark an outdated claim Superseded with a reason; keep results from distinct conditions with their applicability. If the same conditions still conflict and the decision is material, record Conflict with both provenances and safe stop; do not use last-write-wins or call it selected.
6. A revision conflict means the peer changed state after the read. Re-read the common, branches and formal source, reapply the integration Gate, then attempt a new conditional update only if valid. Limit retries according to the adapter. If authority is unavailable, keep facts in the branch as unverified and state which common integration was not done.

## Select, interrupt, archive

After explicit user selection, write the common decision conditionally, then verify it by readback. Only after that readback append each selected, partially selected, or superseded Branch Outcome and its reason/Source; archive both adopted and rejected source branches immediately unless the user explicitly requests continued exploration. For a combined solution, record each branch's adopted portion before archiving. If a common write or readback fails, do not set outcomes or archive related branches. If a later branch operation fails, leave per-record retryable state and report the partial result.

On interruption, save focus, last success, external changes, blocker/failure, non-repeatable operations and next safe step, using Work State `Interrupted`, `Blocked`, or `Failed` as appropriate. Ready implementation uses `Awaiting Review`, never `Completed`. An explicit user close can archive immediately after safe state and readback are stored.

At Last Activity At plus the configured inactivity period (seven days by default), archive an expired branch by changing Lifecycle only. A future Keep Active Until protects it. Compute common activity as the maximum of its own material activity and each Active branch's material activity; any Active branch also prevents automatic common archival. Explicit continuation of an archived branch restores its common record after conditional readback, but restoring common never restores every branch. The scheduler that enumerates records and enforces this policy is a separate task. Legacy records are left alone unless an exact Task Key is explicitly resumed.
