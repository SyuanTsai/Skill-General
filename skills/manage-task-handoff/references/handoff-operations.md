# Handoff operations

Read the machine-readable contract first. These steps govern task-local state; they do not choose a durable-memory system or authorize a new external operation.

## Create or resume

1. Obtain a stable Task Key: an exact external work key such as `jira:ABC-1`, or the origin host task identity when no formal key exists. A new forked conversation inherits its parent's exact Task Key; use its own conversation identity only for Branch ID. Avoid titles, topic similarity, and invented aliases. On explicit continuation, query the configured storage by exact Task Key. No automatic scan on a new conversation.
2. Zero common matches allows one creation when the trigger and unique key are established. One match is reused. More than one stops all writes. Preserve duplicates and report their IDs. An archived common record is restored only for explicit continuation of that same Task Key.
3. Build the seven required common fields from the user request and verified sources. `Intent` states desired outcome and current phase. `Scope` marks clauses Active, Superseded, or Deferred and records constraints and authorization without inventing it. `Current` states focus, material changes, last successful check, unresolved work, and next safe action. `Source` distinguishes formal authority from working copies and includes mutable version, environment, revision, worktree, and their required revalidation. Lifecycle and Work State remain separate.
4. If an A conversation forks B and A already has a branch record, fix A's exact record revision as the fork point and create only the missing B branch. If A has only the common record, fix the pre-fork common revision, A's recoverable host identity, a stable fork point, and distinct A/B Branch IDs before any write. Classify A's pre-fork Current and Source: keep confirmed task-level facts as the shared baseline, but put A-only progress, hypotheses, and candidate conclusions in A's new branch; B starts from that confirmed baseline with its own Current and Source, retaining a traceable reference to the fork snapshot rather than treating A's candidate as selected. If the classification cannot be verified, keep the disputed fact in A and mark the fork pending instead of promoting it to common. Both peer branches inherit the same Task Key, confirmed Intent, and Scope; neither is the task-level main.
5. For a common-only first fork, conditionally write the intended A/B IDs, pre-fork revision, stable per-record Operation IDs, and pending fork status into common Current or equivalent mapped fork metadata, then read it back. Create A from A's preserved Current/Source first, then B from the shared confirmed baseline, using separate create-if-absent operations and the same fork point. Read back each record, association, operation outcome, and the common Active-branch index; conditionally add only missing IDs if another peer advanced the index. After both records and IDs read back, conditionally leave only confirmed shared state, fork provenance, and the peer index in common Current and clear pending; verify that final common readback before either branch writes divergent work. This structural conversion does not select A or B or authorize a direction change. If A already existed, do not recreate it; only B and its index entry need this verified creation sequence.
6. An A, B, event, index, or final common readback failure keeps the stable IDs and pending fork state. Preserve every committed step, report the exact record and Operation ID still missing, and retry only that step; never write A-only changes into common or a peer branch. A branch whose index integration failed remains discoverable only by its exact Branch ID until reconciliation. Do not call the two-peer fork complete or let Task Key-only lookup auto-resume a lone indexed branch while a fork is pending.
7. With Branch ID, exact lookup must return at most one matching branch linked to that Task Key. With only Task Key, read the common Active-branch index. A single Active branch can be resumed only when no fork is pending. For several branches use thread identity or unique request context; ask for a direction only when neither identifies the branch and that ambiguity is material. An explicit continuation of an Archived branch restores the common record for the same key first if needed, then restores only that exact Branch ID, adds it to the common Active index conditionally, and verifies each readback. If a step fails, retain its exact operation ID and report partial restoration; never present an unindexed branch in a Task Key-only lookup. Do not reactivate an Archived branch for read-only inspection.

## Checkpoint and integrate

1. Re-read the applicable formal source and mutable revision on resume. Treat a stored Source locator as an instruction to revalidate, never as automatic authority. Distinguish confirmed requirement from a branch proposal or unverified inference.
2. Compute only material differences for the target common or branch fields. A read, a new conversation, or a no-op write must not change Last Activity At. If the platform's native last-edit time advances on a no-op, the adapter must skip that write; if it advances on maintenance, use a custom material-activity field instead.
3. Use the adapter's conditional write with expected revision/ETag and a stable operation ID. Read back each changed field and revision, then append one immutable event per changed field with composite Operation ID, Record ID, and Field identity, previous and new state, actor/time, reason, Source/evidence, integration status, and verified or unresolved readback result. Read back event identities before calling the checkpoint complete. Never erase older transitions. A retry of the same operation returns the first write outcome without duplicating field events. If a record or event readback fails, preserve the exact operation and pending field keys for reconciliation instead of inventing success.
4. An independently verified fact with a traceable Source and no task-direction effect can be integrated to common automatically. Preserve the originating Branch ID and applicability conditions. Candidate architectures, tradeoffs, selection/rejection/combination, Intent, global Scope, and authorization require user confirmation. Both branches may be Awaiting Review while common still has no selected outcome.
5. For mutually exclusive verified facts, compare actual version, environment, Scope, verification time and method. Record the applicability conditions in the branch's optional Applicability Scope and Source before integration. Revalidate against the adopter's authority source and current work state. Mark an outdated claim Superseded with a reason; keep results from distinct conditions with their applicability. If the same conditions still conflict and the decision is material, record Conflict with both provenances and safe stop; do not use last-write-wins or call it selected.
6. A revision conflict means the peer changed state after the read. Re-read the common, branches and formal source, reapply the integration Gate, then attempt a new conditional update only if valid. Limit retries according to the adapter. If authority is unavailable, keep facts in the branch as unverified and state which common integration was not done.

## Select, interrupt, archive

After explicit user selection, write the common decision conditionally, then verify it by readback. Only after that readback append each selected, partially selected, or superseded Branch Outcome and its reason/Source; archive both adopted and rejected source branches immediately unless the user explicitly requests continued exploration. For a combined solution, record each branch's adopted portion before archiving. If a common write or readback fails, do not set outcomes or archive related branches. If a later branch operation fails, leave per-record retryable state and report the partial result.

On interruption, save focus, last success, external changes, blocker/failure, non-repeatable operations and next safe step, using Work State `Interrupted`, `Blocked`, or `Failed` as appropriate. Ready implementation uses `Awaiting Review`, never `Completed`. An explicit user close can archive immediately after safe state and readback are stored.

At Last Activity At plus the configured inactivity period (seven days by default), archive an expired branch by changing Lifecycle only and then remove its ID from the common Active index with conditional readback. If the index update fails, keep the archived Branch ID and operation IDs as a partial reconciliation job; the common remains protected until the index readback succeeds. A future Keep Active Until protects it. Compute common activity as the maximum of its own material activity and each Active branch's material activity; any Active branch also prevents automatic common archival. Archive expired branches and verify index changes before evaluating whether common can be archived. Explicit continuation of an archived branch restores its common record if needed and only that exact branch; restoring common never restores every branch. The scheduler that enumerates records and enforces this policy is a separate task. Legacy records are left alone unless an exact Task Key is explicitly resumed.
